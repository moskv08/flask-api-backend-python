# Migrate

You are managing an Alembic migration for a Flask + SQLAlchemy + PostgreSQL project.
Migrations are high-risk operations — be conservative, explicit, and always confirm
before applying anything destructive.

## Detect mode

- `/migrate <description>` → **Generate** a new migration for a model change
- `/migrate review` → **Review** the latest migration file without generating or applying
- `/migrate status` → **Status check** of current migration state
- `/migrate rollback` → **Roll back** the last applied migration

---

## Generate mode

### Step 1 — Read the model

Read the relevant file(s) in `/models/`. Understand what changed:
- New table (new model class)
- New column(s)
- Changed column type or nullability
- New relationship / foreign key
- New index or unique constraint
- Column or table removed

Summarize the detected changes to the developer before generating.

### Step 2 — Generate the migration

```bash
uv run alembic revision --autogenerate -m "<description>"
```

Use a clear, lowercase, underscore-separated description that describes the change:
- ✅ `add_email_to_users`
- ✅ `create_posts_table`
- ✅ `add_index_on_user_id_to_posts`
- ❌ `update model`
- ❌ `changes`

### Step 3 — Review the generated file

Read the file in `alembic/versions/`. Check for every item below.

**Things autogenerate misses or gets wrong — always check manually:**

| Issue | What to look for |
|---|---|
| Unique constraints | `UniqueConstraint` in model but not in migration |
| Check constraints | Never autogenerated — must add manually |
| Indexes on FK columns | Often missing — add `op.create_index()` |
| Server defaults | May be missing if set via `server_default` |
| Enum types | PostgreSQL enums need explicit `sa.Enum(...)` |
| Sequence changes | Often ignored |
| Data migrations | Autogenerate never handles these |

**Destructive operations — flag every one of these:**

- 🔴 `op.drop_table()` — dropping a table
- 🔴 `op.drop_column()` — dropping a column (data loss)
- 🔴 `op.alter_column()` with type change — may fail on existing data
- 🔴 Adding `nullable=False` column to a table with existing rows — will fail without a default
- ⚠️ Renaming a column — autogenerate sees this as drop + add (data loss); use `op.alter_column()` with `new_column_name` instead

### Step 4 — Fix the migration if needed

If anything is missing or wrong, fix the migration file directly.
Show the developer the final `upgrade()` and `downgrade()` functions before applying.

Always verify `downgrade()` is the correct inverse of `upgrade()`. If it can't be
reversed cleanly (e.g. dropped columns), add a comment explaining why and what
manual steps a rollback would require.

### Step 5 — Confirm before applying

Show a summary:
```
Migration: <filename>
Changes:
  + add column users.email_verified (Boolean, default False)
  + add index ix_users_email_verified

Destructive operations: none

Apply this migration? (yes / cancel)
```

Wait for confirmation.

### Step 6 — Apply

```bash
docker compose exec flaskapp uv run alembic upgrade head
```

Verify:
```bash
docker compose exec flaskapp uv run alembic current
```

Report success or the full error if it fails.

**If it fails:** do NOT attempt to auto-fix and re-apply. Show the error, explain
the likely cause, and let the developer decide how to proceed.

---

## Review mode (`/migrate review`)

Read the latest migration file in `alembic/versions/` (highest revision number).
Run the same checklist as Step 3 above and report findings.
Do not apply anything.

---

## Status mode (`/migrate status`)

Run:
```bash
docker compose exec flaskapp uv run alembic current
docker compose exec flaskapp uv run alembic history --verbose
```

Show:
- Current revision applied to the DB
- Pending migrations (if any)
- Whether the DB is ahead of, behind, or in sync with the codebase

---

## Rollback mode (`/migrate rollback`)

Show what will be rolled back first:
```bash
docker compose exec flaskapp uv run alembic history -r -1:current
```

Warn explicitly if the downgrade involves:
- 🔴 Data that will be permanently lost (dropped columns, dropped tables)
- 🔴 Enum types being removed
- ⚠️ Indexes being dropped that are currently in use

Ask for confirmation, then:
```bash
docker compose exec flaskapp uv run alembic downgrade -1
```

Verify the rollback:
```bash
docker compose exec flaskapp uv run alembic current
```

---

## General rules

- Never run `alembic upgrade` or `downgrade` without showing the developer what will happen first
- Never edit a migration that has already been applied to a shared or production DB — create a new one instead
- If autogenerate produces an empty migration, it means Alembic didn't detect the model change — check that the model is imported in `env.py`
- If migration state is confused (`alembic current` shows nothing or errors), run `/debug` first
